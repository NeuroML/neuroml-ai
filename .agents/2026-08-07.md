## Errors and Lessons

- NiceGUI: creating UI elements from a bare `background_tasks.create(...)`
  task fails ("slot stack is empty"). Pass async handlers directly as
  `on_click=`; NiceGUI's event dispatch runs them inside the sender's slot
  context. For background-task UI, enter an existing slot explicitly with
  `with container_element:`.
- NiceGUI `app.storage.user` is only guaranteed valid in the initial request
  context of an async page builder -- touch it before the first `await`.
- A `setup_layout` parameter captured by closures is shared by reference;
  `nonlocal user_id` + rebind switches the whole page session's identity
  without threading a mutable holder through 38 call sites.
- The "delete user session" flow must check the DELETE status code; non-200
  means the server data is still intact, so aborting beats minting a new user.
- Session isolation for tests: I initially ran `pytest` from the repo root and
  got ~24 errors; per-package runs (as CI does via `scripts/run_tests.sh`) are
  all green. No real test failures exist.
- `sphinx-build -W`/`-D`/`-T` are not accepted in this Sphinx 9.1.0 install's
  CLI path (`-W` worked only as `-W` on the `sphinx` subcommand form); use
  `sphinx-build docs docs/_build` and pass `-D exclude_patterns=...` to work
  around the typer break, or exclude_patterns via conf.

## Next session: document metadata extraction (investigated, not implemented)

Goal: during the Docling chunking phase, pre-populate the metadata map
(and/or chunk metadata) with common academic-document fields so
researchers can review/confirm instead of hand-filling
`metadata-map.template.json`. Regex extraction is acknowledged as
not-robust, but still worth it as a pre-population aid -- academic
articles should ideally expose ``keywords`` and a ``url``/DOI.

Verified against docling 2.118.1:

- Free structured signals: `result.document.origin` (`filename`,
  `mimetype`, `uri` for web inputs), the `title`-labelled text item,
  and `TextItem.hyperlink` (URLs from markdown/HTML links; reachable
  per chunk via `chunk.meta.doc_items[i].self_ref` -> item lookup).
- NOT populated by default: `keywords`/`topics`/`summary`/`entities`/
  `description` metas (only via docling's opt-in LLM enrichment
  pipeline, needs an LLM backend); PDF Info dict
  (`PdfMetaData`/`Page.meta_data` is a latent model field with zero
  usages in this version); HTML `<meta>` tags are not extracted either.

Planned approach:

- New `klea_utils/stores/metadata_extraction.py`: regex/heuristic scan
  for `Keywords:` / `Key words:`, `Author(s):` / `By:`, `URL:` /
  `Website:`, `DOI:` (+ loose `10.xxxx/...` pattern), plus the free
  structured signals (title, `source_url`, `source_type`, per-chunk
  hyperlink URLs).
- Wire into `StoresBuilder._convert_and_chunk`; pre-fill
  `metadata-map.template.json` (`write_heading_template`) so the user
  reviews/overrides; optionally attach directly to chunk metadata too.
- Open decisions: PDF authors (add `pypdf` to read the Info dict, vs
  skip PDFs, vs regex-on-body only); opt-in `--extract-metadata` flag
  vs on by default; which fields to keep (keywords, authors, url, doi,
  title, source_type); template pre-fill vs direct attach.

Side note: docling PDF conversion in this environment tried to use the
CUDA GPU (Quadro P1000, sm_61) which the installed torch build
(cu130, sm_75+) does not support; force CPU via `CUDA_VISIBLE_DEVICES=""`
when testing PDFs locally.
