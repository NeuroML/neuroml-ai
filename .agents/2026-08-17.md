## 2026-08-17-1545 — profile-based config selection

### Objective

Replace env-file `*_APP_CONFIG_FILE` config selection with profile-based
lookup (`--profile <name>` loads `<name>.json`), plus `--profile template`.

### Decisions and outcomes

- Profiles resolve CWD-first, then the per-app platformdirs config dir.
- `--profile` is carried into the server via the existing
  `KLEA_AGENT_APP_CONFIG_FILE` / `KLEA_RAG_APP_CONFIG_FILE` env var (process
  env beats the env file in pydantic-settings), so no new config env var.
- `--profile template` scaffolds a ready-to-fill config into CWD (refuses to
  overwrite); RAG template includes an `ExampleDomain` placeholder.
- Implemented incrementally across utils/agent/rag; all committed except the
  `deployments/huggingface` submodule edits.

### Errors and lessons

- **Typer single-command collapse**: a `Typer()` with one command becomes a
  flat CLI, so `klea-rag-serve serve <opts>` fails (only `--help` works); the
  canonical form is `klea-rag-serve --host ... --profile ...`.  Pre-existing
  docs/error messages referenced the bogus `serve` subcommand -- corrected
  and documented with a code comment.
- **Docs build broken in the dev venv** (pre-existing): sphinx 9.1.0 +
  sphinxcontrib-typer 0.8.1 incompatibility, reproduced in a minimal project.
  Deferred; likely needs version pins in `requirements-docs.txt`.
- Installing `requirements-docs.txt` replaced editable dev installs with
  stale copies (rag tests imported an old `klea_rag.config`).  Restored with
  `uv pip install -r requirements-dev.txt --reinstall`.  Build docs in a
  separate env, or reinstall dev editable afterwards.

### Open questions

- Pin typer/sphinxcontrib-typer/sphinx for a working docs build.
- Commit the `deployments/huggingface` submodule edits (also has a
  pre-existing dirty `chroma.sqlite3` LFS file).

## 2026-08-17-2143 — MCP bundled tools server + annotations

### Objective

Design and implement MCP tool infrastructure supporting multiple domains:
a shared, tag-configurable bundled tools server plus standard MCP
annotations, so RAG and agent deployments can enable the tools they need
per domain without editing server code.

### Completed

- Confirmed empirically that fastmcp 3.4.7 already supports per-server tool
  filtering via `include_tags`/`exclude_tags` on config entries, and that
  `FastMCP.tool()` accepts an `annotations` kwarg (both reached
  `list_tools()`).
- Implemented (incrementally, review/commit per step) the full plan:
  shared bundled server, tag-based filtering, standard annotations, docs.
- Maintained the agent/RAG config parity: a single `general` section on
  both apps hosts `bundled_tools` (agent on by default, RAG opt-in).
- RAG exposes the bundled server across all its domains (one shared client,
  no duplicate subprocesses).
- Standard MCP annotations adopted for the effect signal rather than a
  third tag axis; tags kept to scope + domain only.

### Errors and lessons

- `mcp_pkg` tests initially failed because the package resolved
  `klea_utils` from a stale installed copy (old `registry.py` without
  annotations support); refreshing the editable install
  (`uv pip install -r requirements-dev.txt`) fixed it.  Lesson: refresh
  editable installs after changing shared-package internals.
- The editor LSP persistently flagged the new `klea_utils.mcp.server`
  module as unresolvable while runtime, `ty`, and pytest all resolved it --
  LSP index staleness, not a real error.
- fastmcp rewrites tool signatures on registration (moving Context after
  params), so tests must check parameter membership, not position.
- A latent flaky test surfaced from set-iteration order; fixed with set
  comparison.
- Docs build needs `sphinxcontrib-typer` (imports as `sphinxcontrib.typer`);
  `make html` needs `requirements-docs.txt` installed.  Was reminded to use
  `uv pip`, not `pip`.

### Notes

- Two-axis model settled and documented: tags = Klea's config filtering
  (which domain's tools); standard MCP annotations = universal behavioral
  contract (read-only/destructive) any host can enforce.
- Final tag vocabulary: scope `local`/`web` + domain/functional (`bundled`,
  `files`, `code`, `download`, `echo`, `neuroml`, `neuroml-db`, `osb`);
  no read/write/exec tag axis.
- Full verification green: 567 tests, `ty` at 29-diag baseline, all 6 CLIs
  start.  Only CHANGELOG left uncommitted at session end (reviewed).

- https://fastmcp.wiki/en/servers/tools#mcp-annotations - ToolAnnotations
  hints and how clients act on them (linked from the ToolInfo docstring).

## 2026-08-17-2157 — env-driven model defaults + graceful no-model handling

### Objective

Make model configuration work cleanly on a fresh machine with no env/config
files: remove hardcoded ollama defaults, make the env file optional, and
fail gracefully (startup warning + clear per-query error) instead of
crashing when no models are set.

### Decisions and outcomes

- Removed hardcoded ollama defaults from model env fields; env vars are now
  the default-model source (shell env > optional env file > "").
- Env file is now optional in `_load_env` (was a hard `FileNotFoundError`).
- Design B: `self.llm_models` is the single source of truth for roles.  The
  pydantic-settings env class is generated from `llm_models` keys via
  `create_model` (`{role}_model` -> `<PREFIX>ROLE_MODEL`), so the env schema
  and model roles cannot drift.  Agent role `reasoning_model` renamed
  `plan_model`; deleted the static `AppEnv` classes.
- Startup: `_check_required_models` logs a warning (not a failure) listing
  every model env var with its current state, so the server still starts and
  the web UI can set models per chat.
- Removed the RAG dev asserts in `_create_graph`; `ClassifyQuestion`
  `output_schema` accepts `None`.
- `_build_invoke_config` raises a clear "No model configured for role 'x'"
  error (was a confusing `OpenAIError: Missing credentials`); flows through
  SSE into the UI notification with a "use Choose models" hint.
- Web UI status pane shows "Not set" for empty roles; `/models/active` now
  reports `required` per role.

### Errors and lessons

- RST docstring rules: a list item must not begin with `:meth:` and
  continuation lines inside bullet/numbered lists confuse sphinx-autodoc
  (docutils standalone parses them fine, sphinx does not).  Use plain
  `` ``code`` `` at the start of list items and keep continuations aligned.
- Docs build in the dev venv is still broken (pre-existing sphinx 9 +
  sphinxcontrib-typer incompatibility); the `-b` flag errors out.  Deferred.

### Open questions

- Commit the `deployments/huggingface` submodule edits (pre-existing dirty
  `chroma.sqlite3` LFS file).
- Pin typer/sphinxcontrib-typer/sphinx for a working docs build.
