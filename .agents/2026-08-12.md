# Follow-up: PyTorch / CUDA install guidance (same day)

## Objective

Help users install the correct PyTorch build for their GPU hardware.
torch is intentionally excluded from default deps because the right
wheel depends on the GPU (newer CUDA builds dropped kernels for older
cards).

## Completed

- **Root cause:** Quadro P1000 = Pascal, CC 6.1. CUDA 12.9+/13.x dropped
  support for CC < 8.0, so torch 2.13.0+cu130 (previously installed in
  the klea-313 venv) reported the GPU but had no sm_61 kernels. The last
  compatible 2.13.0 build is +cu126 (CUDA 12.6).
- **Repo:** added root `requirements-torch.txt` (self-documenting, NOT
  referenced by requirements.txt/dev/docs): how to pick a CUDA build via
  CC, full-pin install commands, note that wheels bundle the CUDA runtime.
  Added "(Optional) PyTorch / CUDA" section to `docs/install.rst`.
- **Venv (klea-313):** `uv pip install --reinstall "torch==2.13.0+cu126"
  --extra-index-url https://download.pytorch.org/whl/cu126`.
  Verified: `torch.version.cuda == 12.6`, GPU 1024x1024 matmul runs,
  no kernel warnings.

## Notes

- The PyTorch index hosts only torch-family + `nvidia-*` wheels, so
  `--extra-index-url` (not `--index-url`) is required to resolve pure
  Python deps from PyPI, and the full `+cu126` local-version pin stops
  uv/pip silently grabbing `+cu130`.
- Left-over `nvidia-*-cu13` packages from the old +cu130 install are
  harmless orphans in the venv.

## Follow-up 2: torch is a transitive dep; torch/torchvision must pair

- **Discovery:** `klea_utils[ingest]` -> `docling` ->
  `docling-slim[standard]` requires `torch>=2.2.2,<3.0.0` +
  `torchvision`, so requirements.txt/dev.txt DO pull torch in
  transitively (via the `full`/`test`/`dev` extras), unpinned and from
  PyPI's default build.  `requirements-torch.txt` header corrected and
  a "Recommended workflow" added (install the pinned build first --
  pip/uv keep it since it satisfies docling's range; `--reinstall` only
  to swap a wrong existing build).
- **torchvision pairing bug:** torchvision's metadata pins only the base
  `torch==X.Y.Z`, so a torchvision `+cu130` wheel beside torch `+cu126`
  installs silently but broke `import torchvision`
  (`RuntimeError: operator torchvision::nms does not exist`).  Docs and
  the requirements file now state torch + torchvision must come from the
  same CUDA index.
- **Venv fix:** `uv pip install --reinstall "torchvision==0.28.0+cu126"`
  -- verified `import torchvision`, `torchvision.ops.nms`, and a
  resnet18 forward on the GPU; `import docling` + `DocumentConverter`
  still import cleanly.
- Docs rebuilt (`make html` clean).

## Follow-up 3: torch install verification script

## Follow-up 4: e2e store-creation retest -- Docling GPU/Triton failure

- **Findings (from a `klea-stores-create chunk` retest on nml-elife/):**
  Docling's auto accelerator detection picked `cuda:0` (Quadro P1000) for
  the RT-DETR layout model. Every page's forward pass failed because Triton
  requires CUDA capability >= 7.0 and the P1000 is CC 6.1; Docling marked
  the pages failed and fell back, so chunking "completed" but with no layout
  analysis and ~11s wasted per page.
- **Fix (docs-only, per user):** forced CPU via env vars is enough -- no
  CLI flag or code option. Documented `DOCLING_DEVICE=cpu` (plus
  `DOCLING_NUM_THREADS`) in `docs/tutorials/create-and-use-rag.rst` and
  `docs/concepts/rag.rst`. `make html` clean.
- **Non-issue confirmed:** `metadata-map.json`/`metadata-map.template.json`
  get picked up by `_find_files` because `.json` is in Docling's
  `FormatToExtensions`, then fail conversion. Left as-is -- correct
  behaviour; source dirs should contain only source files.
